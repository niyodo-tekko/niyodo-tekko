公式サイト 更新手順書
― テキスト修正の反映まで ―

Visual Studio Code を使って公式サイト（niyodo.co.jp）の文章を修正し、GitHub Pages へ公開するまでの標準手順です。誤字の修正、日付や数値の書き換えなど、既存テキストの差し替えを対象としています。

1. 前提情報

公開URLhttps://niyodo.co.jp
リポジトリhttps://github.com/niyodo-tekko/niyodo-tekko
ブランチmain（このブランチへ push した内容がそのまま公開されます）
ローカルフォルダOneDrive ＞ 共有用フォルダ ＞ 公式サイト_仁淀鉄鋼(Github Pagesで公開) ＞ niyodo-tekko
主な編集対象index.html（ニュース・ごあいさつ・会社概要・沿革など全セクションを収録）
map.html（アクセスマップ）
文字コードUTF-8（BOM付き） ※ 保存時の最重要注意点。詳細は「4. 注意事項」参照
公開までの時間push から概ね 1〜3 分
所要時間の目安10 分程度

2. 準備するもの

  • Visual Studio Code（インストール済みであること）
  • GitHub アカウントへのサインイン（VS Code 上で認証済みであること）
  • 修正内容が確定していること（誤字の場合は「修正前の文字列」と「修正後の文字列」を明確にしておく）

3. 修正から公開までの手順

  1. VS Code でリポジトリのフォルダを開く

    VS Code のメニューから ファイル ＞ フォルダーを開く を選び、上記「ローカルフォルダ」を指定します。エクスプローラーでフォルダを右クリックし 「Code で開く」 を選んでも構いません。

    開く前に確認

    OneDrive の同期が完了していること（フォルダのアイコンが緑のチェックになっていること）。同期中に編集すると、index-PC名.html のような競合ファイルが作られることがあります。

  2. 対象ファイルを開き、該当箇所を検索する

    左のエクスプローラーから index.html を開き、Ctrl + F で検索します。

    検索語は、誤字そのものだけでなく前後の文字を含めた 5〜10 文字程度を指定してください。同じ語が他の箇所にも存在する場合の誤修正を防げます。

    検索語の例（「かって」→「かつて」の修正の場合）

    × かって … 「向かって」「分かって」など無関係な箇所にもヒットする
    ○ 企業自身もかってない … 目的の 1 箇所だけに絞り込める

  3. 文字を修正する

    該当箇所を直接書き換えます。HTML タグ（<br> や <a href="..."> など）は消さないよう注意してください。

    修正例

    修正前： 企業自身もかってない変革を迫られています。
    修正後： 企業自身もかつてない変革を迫られています。

  4. 保存前に文字コードを確認する

    VS Code 画面右下のステータスバーを見て、UTF-8 with BOM と表示されていることを確認します。

    もし UTF-8（BOM の表示なし）になっている場合は、そのまま保存するとサイト全体が文字化けする恐れがあります。ステータスバーのエンコーディング表示をクリックし、「エンコード付きで保存」→「UTF-8 with BOM」 を選択してください。

  5. 保存する

    Ctrl + S で保存します。

  6. 差分を確認する ― 最も重要な工程

    Ctrl + Shift + G でソース管理ビューを開き、変更されたファイル名をクリックすると、変更前後が左右に並んで表示されます。

    変更行が、自分が直した行だけになっているかを必ず確認してください。

    大量の行が変更扱いになっていたら中止

    1 文字しか直していないのに何十行も変更されている場合、文字コードまたは改行コードが変わってしまっています。コミットせず、ソース管理ビューでファイル名の横の 「変更を破棄」 をクリックして元に戻し、手順 4 からやり直してください。

  7. コミットする

    ソース管理ビュー上部のメッセージ欄に、何をどう直したかが分かる一文を入力し、「コミット」ボタンを押します。

    コミットメッセージの例

    ごあいさつの誤字修正（かって→かつて）
    会社概要の社員数・売上高を令和8年3月期に更新
    ニュースリリースに2026年4月分を追加

  8. GitHub へ push する

    「変更の同期」（または「Push」）ボタンを押します。これで GitHub 上のリポジトリに反映され、GitHub Pages のビルドが自動的に始まります。

  9. 公開サイトで確認する

    1〜3 分待ってから https://niyodo.co.jp を開き、Ctrl + Shift + R（キャッシュを無視した再読み込み）を押して、修正が反映されていることを目視で確認します。

    反映されない場合は、GitHub リポジトリの Actions タブで pages build and deployment が緑のチェックになっているかを確認し、さらに数分待って再確認してください。

    ここまで確認できたら完了です

    修正箇所が正しく表示され、ページの他の部分（レイアウト・画像・リンク）に崩れがないこともあわせて確認しておくと安心です。

4. 注意事項

メモ帳（notepad.exe）では編集しない

改行コードや文字コードが書き換えられ、ファイル全体が変更扱いになります。差分が追えなくなるため、必ず VS Code を使用してください。

文字コードは UTF-8（BOM付き）を維持する

このサイトの HTML ファイルは BOM 付きで保存されています。BOM を落として保存すると、環境によっては日本語が文字化けします。保存のたびにステータスバーを確認する習慣をつけてください。

main ブランチへの push は即公開を意味する

確認用の環境はありません。push した内容がそのまま公開サイトに反映されます。差分確認（手順 6）を省略しないでください。

GitHub の Web 画面から直接編集した場合

ブラウザ上で編集・コミットした場合、ローカルのフォルダは古いままです。次回の編集前に、VS Code のソース管理ビューから 「プル」 を実行して最新化してください。忘れると次回コミット時に競合が発生します。

公開したくないファイルを追加する場合

リポジトリ直下に置いたファイルは、原則としてそのまま一般公開されます。社内向け資料などを置く場合は、_config.yml の exclude: にファイル名を追記して公開対象から除外してください（本手順書も除外しています）。

exclude:
  - README.md
  - 手順書.html

5. 取り消し方法

状況対応
保存したが、まだコミットしていない ソース管理ビューでファイル名横の 「変更を破棄」 をクリックする
コミットしたが、まだ push していない 正しい内容に修正し、あらためてコミットしてから push する
push して公開されてしまった あらためて正しい内容に修正し、コミット＆push して上書きする（履歴を消す操作は行わない）
判断に迷ったら

差分の内容に不安がある、大量の行が変更されている、競合が発生した ― こうした場合は無理に push せず、その状態のまま担当者に確認してください。push しない限り公開サイトには影響しません。
